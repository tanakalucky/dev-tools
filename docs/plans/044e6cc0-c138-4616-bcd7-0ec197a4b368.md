# 作業計画: PR preview 基盤

## 承認済み方針(レビュー対象として凍結)

### 識別

- 変更 ID: `044e6cc0-c138-4616-bcd7-0ec197a4b368`
- 計画の保存先: このファイル
- レビュー台帳: 同じ変更 ID の外部台帳(リポジトリ外で管理)。回数の正本は台帳だけとする。
- 関連する別の変更: JSON ツール(Draft PR #1、変更 ID `31124888-8bf7-49bd-99bf-ca00ea7650e6`)。
  レビュー枠は別管理で、JSON 側の指摘や延期事項をこの変更へ移さない。

### 目的

JSON ツールの PR を main へマージする前に、その動作を Cloudflare Workers の preview で
確認できるようにする。PR への push で同じ preview を更新し、close / merge で片付ける。

### 承認範囲 A(この計画で実行するもの)

基盤の実装、Draft PR の作成と push、CI、正式な 3 観点レビューまで。
公開 resource は作らない。

### この計画では行わないもの(別途の承認が必要)

- B: Cloudflare 上の preview 用 Worker の作成・更新・削除、実 provider へのアクセス。
- C: 基盤 PR の main へのマージ、main の JSON ブランチへの取り込み。
- 本番 deploy、custom domain、Access、token・environment・ブランチ保護・課金の設定変更。
- 定期実行や周期的な照合。イベント喪失からの自動回復は約束しない。

### 方式

workflow は 3 つで、すべて main の定義として導入する。

1. `preview-build`(`pull_request`: opened / synchronize / reopened)
   secret を使わず、権限は読み取りだけで、PR の head SHA をビルドして成果物を上げる。
   PR のコードが動くのはここだけとする。
2. `preview-deploy`(`workflow_run`: `preview-build` の成功時)
   main の定義で動く。PR のコードは checkout せず、main にある helper と版を固定した
   deploy ツールだけを使う。成果物は作業ツリーの外に展開し、検査してから deploy する。
3. `preview-cleanup`(`pull_request_target`: closed のみ、および手動実行)
   main の定義で動く。PR のコードを checkout も実行もせず、メタデータだけで
   対象の Worker を削除する。失敗は run の失敗として報告し、再試行は手動で行う。

### 安全条件(受け入れ条件)

- Worker 名は `dev-tools-pr-<数字>` に完全一致するものだけを deploy・削除の対象にする。
  本番名 `dev-tools` は対象にできない。名前は PR 番号だけから作る。
- secret を持つジョブは PR のコード・設定を評価しない。成果物はパス、リンク、設定のキー、
  binding、route などを許可リストで検査し、想定外があれば拒否する。
- deploy する head は、上流のビルド実行のメタデータ(起動者、再実行者、head SHA、
  head リポジトリ、PR 番号)を API で照合し、認証済みの owner `tanakalucky` が起動した
  同一リポジトリの現在の head である場合だけを対象にする。commit author や PR 作成者の
  文字列は根拠にしない。
- deploy と cleanup は PR 単位で直列化し、変更の直前に PR の現在の状態と head SHA を
  確認する。閉じた PR の preview を古い実行が作り直さないようにする。
- 明示的な有効化スイッチがない限り、secret に触れる前に終了する。
  この計画の PR とテストで、deploy・削除が副作用として走らないこと。
- 主張しないこと: 競合が起きないこと、および repository secret を他の workflow から
  隔離できたこと。

### 事前確認(実装の前提)

secret と provider へのアクセスなしで、次の 4 点を確認する。確認できなければ実装へ進まず、
根拠と代替案を示してエスカレーションする。

1. 成果物だけの場所で prebuilt の deploy が成立する。
2. deploy 先の Worker 名を成果物の設定で強制できる。
3. deploy 時に、成果物内のコードがローカルで実行されない。
4. provision の既定動作が、検査済みの設定以外の resource を作らない。

### タスクと担当

| 順  | 内容                                                     | 担当                |
| --- | -------------------------------------------------------- | ------------------- |
| 1   | 計画の作成と更新                                         | lead                |
| 2   | 事前確認 4 点                                            | implementer         |
| 3   | workflow、判定・検査の helper とテスト、日本語の手順文書 | implementer         |
| 4   | ブランチの push、Draft PR の作成、CI 結果の取得          | ホスト(lead が依頼) |
| 5   | レビュー資料の作成と、正式な 3 観点レビュー              | lead、reviewer      |
| 6   | P0/P1 の修正と再検証(上限内)                             | implementer、lead   |

### 完了条件とエスカレーション

- 完了: 上記の安全条件を満たす実装があり、実 CI が成功し、3 観点レビューで P0/P1 が
  0 件で、最終スナップショットの照合が通ること。
- レビューは最大 3 ラウンド(失敗・中断を含む)。任意の P2 を理由に追加しない。
- エスカレーション: 事前確認の不成立、3 ラウンド後に残る P0/P1・失敗・未検証、
  その後の未レビュー変更、権限不足、範囲や設計の判断が必要な場合。
- 実際の Cloudflare 上のライフサイクルは、この計画では未実施として残し、B / C の
  判断材料にする。

### 承認の記録

- 承認範囲 A をユーザーが承認(基盤 PR の実装とレビューまで。マージと公開は結果を見て確認)。
- 定期チェックは入れない(ユーザーの指示)。
- 導入順序は「基盤 PR を main へマージ → main を JSON ブランチへ取り込む」(ユーザーの指示。実行は C の承認後)。

- 事前確認の判定(lead の判断): 実装へ進む。根拠と残る不確実性は次のとおり。
  2 と 3 は、本物の token を渡して初めて確かめる条件にはしない。token を使わない検証を
  根拠とし、その範囲と限界をレビュー資料に明記する。
  - 1 は確認済み。合成の最小成果物だけの場所で、prebuilt の dry-run が成立した。
  - 2 は、ループバックの模擬 API と偽の token を使い、dry-run ではない deploy と削除を
    実行して確認した。新規作成、既存の更新、アセット送信、削除のどの経路でも、名前を含む
    リクエストは成果物の設定に書いた preview 用の名前だけを指した。
    限界: 模擬 API は実際の API と応答が異なり得る。実際の API では未検証である。
  - 3 は、同じ検証で確認した。認証後の経路でも成果物のコードは評価されず、送信されるだけ
    だった。外部への接続は検証中すべて遮断し、試行が無いことを確認した。
    限界: 検証した deploy ツールの版と引数に限る。遮断は Node の層で行っており、
    子プロセスやネイティブ経由の接続までは捕捉できない。実際の API の応答による
    別経路は未検証である。
  - 4 は、provision を無効にする指定が受理されることを確認済み。deploy では常に無効にし、
    assets 以外の binding を検査で拒否する。設定の未知のキーは deploy ツール自体も拒否する。
  - この検証は secret なしの回帰テストとして CI で実行する。deploy ツールの版を上げる
    ときは、このテストの成功を条件とする。
  - deploy ツールの利用状況の送信は、実行時に無効にする。
- 配置の判断: JSON 側のブランチと衝突しないよう、ルートに `package.json` と `README.md` を
  置かない。helper と版固定は `.github/preview/`、手順文書は `docs/deploy/` に置く。
