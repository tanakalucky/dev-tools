## 承認済み方針(レビュー対象として凍結)

- レビュー台帳: 外部台帳はこのセッションでは使えない。正本は本ファイル末尾の「レビュー台帳(追記式)」とする。

  レビュー枠は別管理で、JSON 側の指摘や延期事項をこの変更へ移さない。

### 目的

JSON ツールの PR を main へマージする前に、その動作を Cloudflare Workers の preview で
確認できるようにする。PR への push で同じ preview を更新し、close / merge で片付ける。

### 承認範囲 A(この計画で実行するもの)

基盤の実装、Draft PR の作成と push、CI、正式な 3 観点レビューまで。
公開 resource は作らない。

### この計画では行わないもの(別途の承認が必要)

- B: Cloudflare 上の preview 用 Worker の作成・更新・削除、実 provider へのアクセス。
- C: 基盤 PR の main へのマージ、main の JSON ブランチへの取り込み。
- 本番 deploy、custom domain、Access、token・environment・ブランチ保護・課金の設定変更。
- 定期実行や周期的な照合。イベント喪失からの自動回復は約束しない。

### 方式(改訂版、ユーザー承認済み)

独自の build / deploy 基盤をやめ、Cloudflare 公式の Worker Previews に寄せる。
旧方式(`preview-build` / `preview-deploy` と PR ごとの別 Worker `dev-tools-pr-<n>`)は廃止する。

1. 作成・更新: Workers Builds(Cloudflare 側の設定、このリポジトリの変更ではない)。
   Worker `dev-tools` の非本番ブランチへの push で、Preview 用 build
   (`CLOUDFLARE_PREVIEW_BUILD=true npm run build`)のあと `npx cf previews deploy --prebuilt` を実行する。
   根拠: cf/config + Vite plugin 2 の出力は Build Output(`.cloudflare/output/v0`)で、
   `wrangler preview` はこれを読めない(4.149.0 の配布物で確認)。`cf previews deploy` は読める。
2. 削除: `preview-cleanup`(`pull_request_target`: closed、および手動実行)だけを GitHub Actions に残す。
   PR のコードは checkout も実行もせず、版を固定した `wrangler preview delete` で Preview を消す。

### 安全条件(受け入れ条件、改訂版)

- Preview 名は作成・削除ともブランチ名そのもの(`pr-<n>` は使わない)。削除対象は Worker `dev-tools`
  の Preview だけで、Worker 本体を消す経路を持たない。
- 削除は同一リポジトリの head を持つ PR だけを対象とし、同じブランチの open な PR が残っていれば行わない。
  fork PR では secret を使う step に到達しない。
- 削除する名前は git のブランチ名として正しいものだけを受け付ける(`.`・`..` は Worker 本体を指しうるため必ず拒否)。
  手動実行は既定ブランチの定義からだけ受け付ける。
- secret は削除 step の `env` にだけ渡す。PR 由来の値はシェルに直接埋め込まず `env` 経由で渡す。
- 明示的な有効化スイッチ(`PREVIEW_CLEANUP_ENABLED`)がない限り、secret に触れる前に終了する。
- 定期実行は入れない。イベント喪失からの自動回復は約束しない。

### 完了条件とエスカレーション

- 完了: 上記の安全条件を満たす実装があり、実 CI が成功し、3 観点レビューで P0/P1 が
  0 件で、最終スナップショットの照合が通ること。
- レビューは最大 3 ラウンド(失敗・中断を含む)。任意の P2 を理由に追加しない。
- エスカレーション: 3 ラウンド後に残る P0/P1・失敗・未検証、
  その後の未レビュー変更、権限不足、範囲や設計の判断が必要な場合。
- 実際の Cloudflare 上のライフサイクルは、この計画では未実施として残し、B / C の
  判断材料にする。

### 承認の記録

- 定期チェックは入れない(ユーザーの指示)。
- 導入順序は「基盤 PR を main へマージ → main を JSON ブランチへ取り込む」(ユーザーの指示。実行は C の承認後)。
- 配置の判断: JSON 側のブランチと衝突しないよう、ルートに `package.json` と `README.md` を
