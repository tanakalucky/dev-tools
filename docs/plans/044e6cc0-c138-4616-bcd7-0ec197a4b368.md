# 作業計画: PR preview 基盤

## 承認済み方針(レビュー対象として凍結)

### 識別

- 変更 ID: `044e6cc0-c138-4616-bcd7-0ec197a4b368`
- 計画の保存先: このファイル
- レビュー台帳: 消費回数の正本は本ファイル末尾の「レビュー台帳(追記式)」(2/3 消費)。
  workflow-kit の外部台帳(helper)は同じ ID を 0/3 のまま持つが、この変更では使わない。復旧も強制もできていない。
  残り 1 回は、PM が本ファイルの追記式台帳に 1 度だけ予約してから 3 観点レビューを行う(例外的な引継ぎ方針)。
  予約前にレビューを開始しない。新しいキー・ID・状態ディレクトリ、リセット、実際に無い開始の記録は作らない。
- 関連する別の変更: JSON ツール(Draft PR #1、変更 ID `31124888-8bf7-49bd-99bf-ca00ea7650e6`)。
  レビュー枠は別管理で、JSON 側の指摘や延期事項をこの変更へ移さない。

### 目的

JSON ツールの PR を main へマージする前に、その動作を Cloudflare Workers の preview で
確認できるようにする。PR への push で同じ preview を更新し、close / merge で片付ける。

### 承認範囲 A(この計画で実行するもの)

基盤の実装とテスト、新しい Draft 基盤 PR の push と CI、(PM の予約後の)正式な 3 観点レビューまで。
push と GitHub 操作はホストが行う。有効化スイッチはレビュー後のユーザー指示で削除した(承認の記録を参照)。

### この計画では行わないもの(別途の承認が必要)

- B: Cloudflare 上の Preview の実際の作成・更新・削除、provider への接続、手動作成済みの
  Worker `dev-tools` と Preview `feat/json-formatter` への操作。
- C: 基盤 PR の main へのマージ、main の JSON ブランチへの取り込み。
- 本番 deploy、custom domain、Access、Secrets / variables / token / environment / ブランチ保護 / 課金の設定変更。
- Workers Builds の利用。定期実行や周期的な照合。

### 方式(最小構成、2026-10-10 の最新承認)

全ライフサイクルを GitHub Actions で行う。Workers Builds は使わない。workflow は 2 本だけ
(ほかに通常 CI の `preview-infra-test`)。実装とテストは Sonnet の implementer に委任し、Opus は統括と計画だけを行う。
保持する点: Cloudflare 公式の native Preview(Worker `dev-tools` の Preview、別 Worker は作らない)、
Preview 名はブランチ名そのもの、既存の削除経路とその安全条件、定期チェックなし、既存 Secrets 名
(`CLOUDFLARE_ACCOUNT_ID` / `CLOUDFLARE_API_TOKEN`、値は読まない)。

1. 作成・更新(`preview-deploy`、`pull_request`: opened / synchronize / reopened、job は 1 つ):
   PR の head を checkout → `npm ci` → `CLOUDFLARE_PREVIEW_BUILD=true npm run build` →
   アプリが固定している `cf` で `cf previews deploy <ブランチ名> --prebuilt`。
2. 削除(`preview-cleanup`、`pull_request_target`: closed と手動実行): 既存のまま。deploy と同じ
   concurrency group に入れる。

採用しないもの: build と deploy の分離(`workflow_run`)、artifact の隔離と ZIP 解析、Build Output の検査、
独自の deploy 管理コード、`.github/preview` への `cf` の版固定。前版で途中まで作ったこれらのコードは公開対象にしない。

### 安全条件(受け入れ条件、最小構成)

信頼モデル(ユーザーが受け入れ済み): 対象は本人が管理し信頼する PR だけ。build と deploy は同じ job で動くため、
PR の build コードは後続の deploy step の secret に影響しうる。これを隔離で防ぐことはしない。

作成・更新:

- job は次をすべて満たすときだけ動く(有効化スイッチは無い):
  head が同一リポジトリ(fork 排除)、`github.actor` と `github.triggering_actor`(再実行者)がともに
  リポジトリ owner(GitHub が認証した login と数値 ID)。PR 作者名や commit author の文字列は根拠にしない。
- 権限は `contents: read` と `pull-requests: read` だけ。checkout は `persist-credentials: false`。
- secret は deploy step の `env` にだけ渡す。値を表示・保存・外部送信しない。
- Preview 名は PR の head ブランチ名を `env` 経由で渡し(`run:` に直接埋め込まない)、削除と同じ名前検査を通してから
  `cf previews deploy` の位置引数に渡す。特定のブランチ名に固定しない。本番 deploy のコマンドは持たない。
- close との競合: deploy と cleanup をブランチ単位の同じ concurrency group で直列化し、deploy 直前に
  PR が open で head SHA がこの run のものと一致することを確認する。一致しなければ deploy しない。
- ルートに `package.json` が無い PR(基盤 PR 自身など)では何もしない。

削除(保持):

- 削除対象は Worker `dev-tools` の Preview だけで、Worker 本体を消す経路を持たない。
- 削除は同一リポジトリの head を持つ PR だけを対象とし、同じブランチの open な PR が残っていれば行わない。
  fork PR では secret を使う step に到達しない。
- 名前は git のブランチ名として正しいものだけを受け付ける(`.`・`..` は必ず拒否)。deploy も同じ検査を使う。
  手動実行は既定ブランチの定義からだけ受け付ける。
- 有効化スイッチ(`PREVIEW_CLEANUP_ENABLED`)は削除した。上の条件を満たせば削除が動く。

主張しないこと: PR の build コードからの secret の隔離、イベント喪失からの自動回復(手動の再実行で対処)、
完全な回復保証、アカウント全体の隔離、実 Cloudflare 上での動作(deploy 経路は未実行。削除経路は模擬 API での確認だけ。
旧別 Worker 方式の模擬結果は根拠にしない)。`pull_request` の workflow は PR 側の定義で動くため、
上記の条件は PR 側で書き換えられる(本人管理の PR に限る前提で受け入れ)。

### 完了条件とエスカレーション

- 完了: 上記の安全条件を満たす実装があり、実 CI が成功し、3 観点レビューで P0/P1 が
  0 件で、最終スナップショットの照合が通ること。
- レビューは最大 3 ラウンド(失敗・中断を含む)。任意の P2 を理由に追加しない。
- エスカレーション: 3 ラウンド後に残る P0/P1・失敗・未検証、
  その後の未レビュー変更、権限不足、範囲や設計の判断が必要な場合。
- 実際の Cloudflare 上のライフサイクルは、この計画では未実施として残し、B / C の
  判断材料にする。基盤 PR 自身にはアプリが無いため、deploy 経路(build と `cf previews deploy`)の実 CI は
  基盤 PR では確認できない(`preview-infra-test` と、`package.json` が無いときに何もしないことの確認まで)。
